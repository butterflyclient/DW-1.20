REPLAY DW CHAT DELIVERY AND REST AUDIT - 2026-10-06

Issue
Replay could drop a peer's first text message before its delayed join arrived.
The native handler requires the sender to exist in the channel member pool.

Exact target research
Untouched Replay image SHA256:
68fb1cbcb2924182724004039de55a4c50152bb6561803c4898b7930b38132f0
0x140F3D410: OnChatChannelMessage finds the active chat, applies sender privacy
flags, then drops the message if GetMemberFromChatById cannot find the sender.
0x141B316F0: AddMessageToChat stores incoming records in a shared 1200-element
pool of 576-byte messages. Each chat has its own 1200-pointer ring at +11248.
The message text buffer is 500 bytes including its terminator. Incoming state
is 2; owner pointer and channel ID bind the record to the actual native chat.

Fix
The channel service carries a real committed sender-join snapshot with a first
message when the sender joined after the recipient. The serialized endpoint
writer publishes that join before the message and coalesces its delayed copy.
Actor and recipient generations are revalidated before delivery. Publication
history is bounded and owned by the connection, and leaves retire its entry.
No native state is guessed, written, or bypassed. Sender privacy flags remain.
Text chat/clanChat reject missing or embedded NULs and bodies over 500 bytes.
Other channel categories retain their existing bounded binary payload support.
