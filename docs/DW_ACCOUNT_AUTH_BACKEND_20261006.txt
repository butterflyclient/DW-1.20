IMPLEMENTATION
The existing encrypted REST task 255/10 now supports these original Replay routes:
  uno / UnoRes / updatesecuredfields
    PUT /v1.0/users/{owned-user}/securedfields/?client=replaylocal
  uno / UserResource / authenticateUser

  umbrella / UserResource / linkUser
    PUT /v1.0/users/crossplatform/{owned-user}/?client=replaylocal
  umbrella / Umbrella / updateUmbrellaAccount
    POST /v1.0/tokens/uno/?client=replaylocal

Upgrade accepts the target writer's optional userName, email, password,
firstName, lastName, dateOfBirth and country fields, mandatory accountType=full
and boolean subscriptionOptIn. Authentication uses the target email/password
grant. Link uses unoIDToken, accessToken and refreshToken, plus the current
Umbrella Authorization header. Umbrella upgrade uses accountID and the nested
accessToken/refreshToken pair. Ambiguous JSON keys, unsupported fields, wrong
methods, path/query aliases and mismatched account paths are rejected.

These routes augment the existing signed machine-owned player. They do not
provision a different player, accept another player's credentials, invent a
retail account or change the existing user/platform IDs. The original native
197/10 and 197/11 aliases continue to identify this local player. Optional
email credentials are attached through an authorized native upgrade request;
ordinary signed machine login still works without any email/password setup.
Cross-player account migration and retail account ownership are separate scopes.

No password text is persisted. Verifiers use independently salted 16-byte
salts, PBKDF2-HMAC-SHA256 with 200000 rounds and a 32-byte result. Exact password
retries retain the existing salt and durable record. Email uniqueness follows
the local case-insensitive account policy. Full-account metadata lives in
data/platform-accounts/{owned-user}.json; no display-name copy is kept there.
The existing platform profile remains the canonical display-name store.

UNO ID/access/refresh tokens are separate random grants for each live signed
lobby session. The backend checks the player, title, IV seed, session key and
expiration. It does not accept token triples mixed between sessions or accounts.
Credential changes revoke all of this player's previous UNO grants, including
other live sessions. Backend restart and native reauthentication invalidate old
grants. Link and Umbrella upgrade publish owned link/upgrade state before replying.
The existing rename handler now also accepts a current owned UNO access token.
The INI's explicit player_name remains a signed-login display-name override.

DURABLE PUBLICATION
An upgrade can change a credential record and the existing 56-byte identity's
name together. A flushed publication intent binds the old/new identity bytes,
the previous account-document hash, the complete new account record and the
credential-revocation decision. It contains no password text or issued token.
Only identity bytes at +20 onward may change; magic, version and IDs remain intact.

The backend preflights ownership and schema before publishing either file,
then atomically replaces the account document and identity, updates canonical
memory and retires the intent. Recovery accepts only the exact before/after
images and never overwrites unrelated persisted data. An interrupted write
does not report success. Its durable intent can finish during the next affected
account request or server initialization. A changed or corrupt image blocks
recovery rather than being repaired into a different owner.

Affected-account recovery runs before checking its mutation token: recovery
may revoke that token. A stale token cannot authorize a second credential
update after the first interrupted update finishes. Player-specific lookups and
logins recover only that player's intent, leaving other owners available.
Global username searches require a consistent complete name inventory. Server
initialization validates and recovers the persisted inventory before listening.
