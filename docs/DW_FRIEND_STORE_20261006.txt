REPLAY DW FRIENDSHIP PERSISTENCE AND NATIVE LIFECYCLE - 2026-10-06

Issue and implementation
The previous social loader silently accepted duplicate JSON keys. Its friend
handler checked the outer arrays but did not validate every stored account,
relationship pair or pending invitation before reading and publishing changes.
Malformed account types, self relationships, reversed duplicate edges and
inconsistent pending consent could therefore survive a later mutation.

The complete private friend-store layout is now validated before reads and
mutations, and again before publication. It contains exactly schema/context/
friends/pending. Accounts contain one bounded UInt64 userID and uno/bnet type.
Relationship pairs must be distinct and unique regardless of ordering. Pending
pairs must be distinct and unique, and must not already be accepted. Optional
inviting names must fit the native 64-byte name cache including the #0 suffix.
Both arrays retain the 4096-record storage bound. Damaged stores produce an
explicit persistence error without rewriting the damaged bytes.

Registered provider aliases reconcile on a private in-memory copy. Reads never
rewrite existing bytes. An authenticated mutation atomically publishes the
canonical graph after preflighting its native response. Failed publication
acknowledges no success and queues no relationship notification. Social JSON
input and persisted JSON reject duplicate keys and excessive nesting. Responses
retain the shared native 256 KiB REST limit.

This changes backend private persistence validation, not game layouts, native
friend task IDs, authentication or client identity creation. No new human
profiles or initial friendships are provisioned. Unregistered account policy
remains separate; this pass does not claim to implement retail account lookup.
