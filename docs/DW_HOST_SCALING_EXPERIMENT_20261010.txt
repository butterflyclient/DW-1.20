Replay high-population host experiment

Current production workflow: build-game.ps1, then deploy-game.ps1 in E:\DW\IW8.
Only game_dx12_ship_replay_dw.exe is supported. Bot optimizations are included
in this one target. Revision notes and old filenames below are historical
evidence; do not use their former private build commands. See DW_CLIENT_BUILD.txt.

Scope
Thirteen host/navigation routines are replaced by freshly compiled C++ in the private DW
EXE. Their identities, extents, relocation targets and unwind placement come
from the normal Replay compiler. No existing executable is edited in place.
All code and build outputs for this experiment remain under E:\DW\IW8.

Controls
com_optimized 0: use the original scheduling and visibility behavior.
com_optimized 1: CPU optimizations, including this experiment; native scene quality.
com_optimized 2: the same CPU changes plus the existing reduced-detail profile.
The existing registration default remains 1.
sv_hostScaleStatus prints cumulative diagnostic counters. It is not a switch.
Collision ownership fixes apply in every profile: freeing an in-use physics
shape is a correctness failure, not an optional optimization.

Changes
1. Bot movement uses the existing native user-movement worker queue above 20
   connected clients. Commands remain complete 264-byte records; the six-entry,
   1600-byte per-client queue retains its native publication/wakeup ownership.
   Every queued bot command is joined before this routine returns. This matters
   because the caller resets the skeleton cache and updates agents immediately
   afterward. Human commands, spectator buttons, command times and native
   acknowledgement behavior remain on their original paths.

2. A full command queue can use the native worker-draining wait instead of
   repeatedly sleeping for 1 ms. This path applies to human burst input too.
   Worker eligibility, dependency handling, physics context and completion stay
   owned by native routines. Small sessions and com_optimized 0 retain the wait.

3. Bot perception is budgeted above 20 connected clients. The native routine
   evaluates all eligible sentients for threat updates and sorts them by its
   original age/distance priority. It then limits new background visibility
   evaluations to 8 at 21-64 clients, 6 at 65-100, and 4 above 100. An acquired
   target gets its normal check separately. Existing visibility timestamps and
   the native priority age move deferred candidates forward on later frames.
   This visibility routine does not change movement or simulation ticks.
   The deliberate tradeoff is slower perception of secondary/new enemies in
   dense battles. This is an experimental AI scheduling policy, not a claim of
   identical bot reactions.

4. The native bot command-production loop is compiled from C++ and staggers
   full decision updates above 20 occupied slots. Revision 4 adapts the rate to
   population and human proximity. Background searching bots target 96 ms at
   21-64 clients, 128 ms at 65-100, and 192 ms above 100. Background fighting
   bots target 64 ms up to 100 clients and 96 ms above 100. Those background
   intervals double when the closest living human is more than 4096 units away.
   A bot targeting a human, or fighting within 256 units of one, uses 32 ms.
   Searching within 512 units of a human uses 64 ms. Human origins are gathered
   once per server frame, rather than rescanning client records for each bot.
   These intervals round up to the native server frame step.
   A per-slot phase spreads work across frames. Every playing bot still gets a
   complete movement command with current server/command/input times each tick.
   Health/target changes, pending script buttons, inactive/spectator transitions,
   owner changes and time rewinds invalidate cached decisions. Human clients
   keep native processing. Movement and server tick rates are not reduced.
   This deliberately trades background decision/aim refresh frequency for CPU
   headroom; it does not promise identical bot reactions to the unmodified game.

5. Individual and combined collision unload state now means that ANY of the
   five target-build physics worlds still owns world-collision or static-model
   bodies. Setup readiness retains the native ALL-world predicate. This keeps
   fastfile memory resident until both server worlds and all client worlds have
   completed teardown, without suppressing raycasts or removing collisions.

6. sv_hostScaleStatus also reports full/reused bot decisions and average/peak
   elapsed time in bot command generation and movement. These measurements do
   not include the remainder of the server frame (GSC, snapshots, etc.).

7. Revision 3 directly addresses the measured script-navigation hotspot. Only
   bot GetClosestReachablePointOnNavmesh calls above 20 occupied slots, with
   com_optimized 1/2 and the verified native 2D navigator, enter a bounded search.
   The native spatial walker, loose-area walker, and incremental island search
   are recompiled in C++. Native filter predicates, visitation generations,
   traversal order, queue allocation/growth/free and area-handle ownership are
   preserved when no bot budget is active. A thread-owned query scope prevents
   another worker's navigation from consuming the server's budget.

   Each admitted query receives 512 spatial work units and 2048 graph-edge
   visits. A server frame permits at most 8192 spatial units and 32768 edges.
   Occupied-slot groups rotate each native frame, admitting at most 16 slots
   (15 per frame for a full 150-slot population). A 150-slot rotation completes
   in ten server frames. These are work limits, not promised millisecond limits.
   Movement commands and human navigation retain their native rate and path.

   Matching goal points can be reused for less than 250 ms, bound to navigator,
   current area, space, player storage, requested coordinates and path settings.
   No native area handle or graph allocation is kept in the cache. A deferred
   query, or a search finding no reachable area inside its budget, projects the
   requested position onto the bot's current valid navigation area. This can
   delay long routes and make dense-population bots less decisive; it never
   claims that a disconnected region is connected. Mode 0, humans, 3D navigators
   and populations of 20 or fewer keep the original unbounded behavior.
   sv_hostScaleStatus includes query/cache/fallback/spatial/graph counters.

8. The private build also carries the latest DW authentication-address getter
   binding. Its helper was already in current source, but older shared editor
   metadata bound only the port getter. The strict endpoint fixture caught this
   mismatch before publication. The getter is now compiled from source and
   bound privately using the verified native ABI; no runtime binary patch or
   edit to the other session's saved workstation state is required.

9. Revision 4 replaces the native BFX Planner::GetClosestArea body with an
   exact-result search optimization. Profiles 1/2 first call its original
   nearest-area query with a 1024-unit radius. If no valid nearby area is found,
   the temporary result allocation is released and the original unrestricted
   query runs. If a valid nearby area exists, every closer area is also within
   that radius. The native collector retains projection, traversal flags,
   distance ranking and native area storage; no native pointer is cached.
   Profile 0 uses the original unrestricted query directly. This path is not
   subject to the experimental bot reachability work budget in item 7.
   sv_hostScaleStatus counts nearby queries and unrestricted fallbacks so its
   effectiveness can be checked on the actual map.

Research
The original Replay image SHA256 is
68fb1cbcb2924182724004039de55a4c50152bb6561803c4898b7930b38132f0.
Original instructions show bot command application is serial, while normal
client movement already has a worker queue. PreThink copies the same command
that the serial path copies; the worker calls the corresponding native movement
body. The native sight loop can continue over its entire sorted list whenever
a bot has a nearby enemy. This permits quadratic tracing in dense populations.
Native end-of-frame and human movement workers were already enabled. The
later-build deferred-snapshot controls do not exist in this Replay image and
were not fabricated. No applicable BAP mode was identified in the searched
Replay code and reference source.

The target layout differs from the reference source: Replay's team flags here
have five 32-bit words (160 bits), its sentients are 184 bytes, per-sentient
visibility records are 64 bytes, entities are 1440 bytes, and the native sight
candidate array holds 272 entries. The C++ views and compile-time checks retain
these target values. Game mode limits and the native 200-client storage capacity
are not changed by this work.
