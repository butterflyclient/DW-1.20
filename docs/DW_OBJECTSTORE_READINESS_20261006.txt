REPLAY DW OBJECT-STORE UPLOAD READINESS
2026-10-06

Issue
An interrupted multi-object upload could leave only some profile objects saved.
Subsequent reads could expose that partial window. Windows letter-case aliases
also allowed two requested names to target the same stored file.

Research
Replay task 193/7 uses the existing PUT struct-buffer and objects/errors/
validationTokens response. Task 193/6 reads the same opaque profile documents.
The old writer validated a batch, then published its objects individually.
A real failure opening the second object's pending file reproduced partial disk
publication. Backend dispatch already serializes participating reads/writes.
Windows filename comparisons required case-aware destination deduplication.

Fix
A per-title/account journal binds the entire validated window, including exact
contents, metadata, versions and tags. Prepared intent and each object are
flushed before replacement. A failed upload returns a storage error. Reads
recover the complete pending window before returning any object data; recovery
failure blocks those reads. Both supported uno/bnet aliases share one account
journal. Recovery preflights all entries and deduplicates Windows destinations
before replacing a file. Foreign, escaping, corrupt or duplicated intents fail
closed. Recovery retains versions/timestamps and emits no invented callback.
The guarantee is recoverable roll-forward, not rollback of already written files.
No engine recompile, proxy DLL, new port, profile replacement or friend seed.
