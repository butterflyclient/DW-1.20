WHY THE PRIVATE TEST BUILD WAS NECESSARY

Separate LOCALAPPDATA directories isolate first-launch identity creation, but
the original engine still shares its Documents settings and fs_basepath DCache.
The first two-game build authenticated both players, then the second instance
reported that toc1.dcache was locked. This was a native filesystem collision,
not a failed Demonware protocol task.

Original Replay instructions identify the Documents helper at 0x1413FB0D0,
FS_FOpenFileReadWrite at 0x1413D9900, FS_BuildOSPath at 0x1413D8B10 and its handle
owner at 0x1413DA2D0. integration/testing/DW_TestHomePath.cpp reconstructs the
complete path/helper behavior and routes only the four exact DCache leaf names
to REPLAY_DW_TEST_HOME. Assets retain the original game fs_basepath. Native OS
open modes, handle ownership and main/DB/render/server thread selection remain
in their original consumers. The shared complete dvar layout is retained.

The override requires the DW executable, a valid opt-in and an absolute bounded
environment path. Invalid explicit paths fail empty. The production deployment
tool rejects images containing this private helper. This test source must not
be imported into the normal shipping build. It is not a rendering workaround.

The private linked image passed source/object checks, relocation review, zero
unresolved symbols and 28 executed helper/cache checks. OS and handle boundaries
are simulated in those VM checks. The subsequent actual simultaneous processes
prove native profile/cache separation; VM checks alone would not do so.
