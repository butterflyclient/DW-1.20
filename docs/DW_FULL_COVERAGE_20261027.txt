REPLAY DW FULL COVERAGE, LOCAL PARITY AND UNIVERSAL BACKEND - 2026-10-27

1. NATIVE BASELINE (what the game can ask for)

tools/inventory-dw-task-baseline.py builds the reference from the untouched
original image, not from logs or source guesses. Every native DemonWare
request reaches the wire through a small set of SDK entry points that take
literal service/task bytes:
  bdTaskParams::bdTaskParams            0x142156330  dl=service r8b=task
  bdRemoteTaskManager::initTaskBuffer   0x1421170B0  dl=service r8b=task
  bdRemoteTaskManager::startStructTask  0x142117C10  r8d=service r9d=task
  bdRemoteTaskManager::startLSGTask     0x1421179A0  r8=service r9=task
  bdAchievementsEngineService::startTask 0x142118270 service 125, r8=task
  q_bdMW4Service::startTask             0x14213C990  service 197, r8=task
  bdCrossPlatformIdentity::startTask    0x142139930  service 197, r8=task
All rel32 call/jmp sites in executable sections are scanned (the exported
callgraph table is incomplete); argument registers are traced back through
moves, cmov alternatives and spilled stack slots; forwarded arguments are
resolved at the forwarder's own call sites. Result: 124 native routes, zero
unresolved call sites. REST writers come from the exact-image REST inventory
(28 service/resource/operation rows).

With --server the tool also probes a disposable backend (isolated data and
ports) with every route and classifies the logged operation. Current build:
  native 124/124 handled, REST 28/28 handled (abtesting/enroll: the native
  writer leaves serviceName empty and its own SDK validator rejects it before
  sending; the explicit "abtesting" route is served for correct writers).
Receipt: validation/20261027-dw-task-baseline.json

Per-build profile: tools/dw-build-profiles/replay120.json names the image,
its hash, the symbol database and the entry points above. Another game build
gets its own profile; the tool itself has no Replay addresses.

Reachability, for the record: the shipped client never issues these six.
OnlineStorage::ExecuteTask's category branches have no enqueuer that sets
their task kinds; bdObjectStoreStreaming::start's only caller passes mode 1,
so upload modes 2/4 never run; every initDownload call site passes null
extended metadata, so _preDownloadPage never runs. They are served anyway for
other SDK builds and modified clients.

3. HIDDEN PUBLISHER OBJECT

Every login requests 193/8 publisher object infinityward/7617664569516336902.
The name is XOR-decrypted at run time inside control-flow-flattened code in
sub_1415285B0 (live frame); the downloaded buffer is stored and released, not

handles. Publishing a file with that name under objectstore/publisher serves it.

5. LOCAL SERVER PARITY

A fresh data folder used to start without QoS/relay, with an empty Store,
default-only publisher variables, and no Battle Pass, leaderboards,
playlists, marketing, achievement definitions or dashboard operator key.

Content packs (content/<pack>/manifest.json + files/) hold the primary
server's published, non-player content. tools/sync-content-pack.py snapshots
it read-only from the droplet (--from-droplet) or any data folder; player
data, keys, sessions, logs, backups, updates and maps are never selected.
At startup the backend installs every pack found beside its executable
(src/content_pack.cpp): missing files are added, files still holding an older
pack's bytes are updated, operator-published or edited files are kept, and
nothing is deleted (state: <data>/content-packs/<pack>.json). Disposable
fixture servers (--port-offset) and --provision runs never seed; use
--content-pack <dir> or --no-content-pack to choose explicitly.

Signed content: the two publisher patch manifests (1_manifest_patch/comms_pc_
8.19.txt) carry an RSA-PSS signature (salt 8) over the native manifest digest,
verified by the client at 0x141038500 against the key the client trusts. The
local client trusts only its own server's key, so the droplet-signed copies
failed the "checking for update" patch fence with error_codes/4_48 (TORCH).
At startup the backend now verifies zero-entry manifests against its own
platform key and re-signs them when needed (metadata checksum/version
follow); the pack state records which pack file each local signature came
from, so restarts are idempotent and a newer pack still applies. Marketing
messages in the pack are unsigned; no other packed content is key-bound.

A loopback-only server also creates operator-access.key for the dashboard's
start-match/fill-bot controls. When <data>/local-play.json names the game
folder, the server writes playlists/<title>/packages.json from the actual
installed maps (custom maps in mods/mw120r/maps, junctioned folders handled),
so matchmaking only selects maps this PC has.

One command: Host-Local-Server.ps1 (or Run_Replay_DW_Local_Server.cmd) builds
if needed, starts the server, creates or refreshes the local client when the
production EXE updated or the server key changed (INI kept, old files backed
up in dw-local-client-backup/), and launches the game. -Stop stops only the
server it started; -StopWhenGameExits stops it after the game closes.

6. UNIVERSAL BACKEND DIRECTION

Version-specific facts live in data, not code paths, for new work:
  tools/dw-build-profiles/<build>.json  image, symbols, SDK entry points
  content/<pack>/manifest.json          titles, build, published content
Packs are title-scoped by path, so several game versions can be served from
one data folder. Existing services already key storage by title ID; new
title support starts with a build profile (to get its baseline), a content
pack, and handlers for any routes the baseline marks unhandled.
