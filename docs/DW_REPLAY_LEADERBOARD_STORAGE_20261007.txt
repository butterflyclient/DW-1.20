REPLAY LEADERBOARD STORAGE/NAMESPACE INTEGRATION - 2026-10-07

Issue
Native stat writes use a base/tracked board ID. UI reads add 140000 or 150000.
The backend previously treated each resulting number as a separate stored board,
so a successful native write could remain invisible to a later UI request.
The write path also rejected valid wide rows accepted by the projected reader.

tools/research-leaderboard-namespaces.py executes original LB_GetByRank

Implementation
Publication schema 2 adds an explicit storage_board alongside the complete
column layout. The generator derives it from the shipped base/tracked/view IDs.
All 747 current definitions are regenerated. Query handlers load the published
layout once per requested board and resolve its storage ID before selecting rows.
The original requested ID remains in matrix replies. Arbitrary client prefixes
are never stripped automatically, and old unaliased schemas remain supported.
These aliases are a local backend implementation choice derived from native
write/read contracts, not a claim about retail Demonware's internal storage.
The current emulator targets PC Replay accounts; distinct cross-platform
population/filtering beyond that target remains a separate integration scope.

leaderboard_row.h defines and validates the complete shared persistent row:
nullable signed Int64 rating, up to 240 nullable signed Int32 columns, bounded
optional name and nonnegative update time. Both read and write paths use it.
Native writes still accept at most ten packet columns. Replace/add/max and NAN
updates preserve untouched fields, including the wide tail. An invalid tail,
late arithmetic overflow or foreign-owner row rejects the entire batch before
publication. Projected responses remain bounded to the native ten-column reader.
