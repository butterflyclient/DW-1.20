ISSUE AND RESEARCH
Replay independently prepares its tournament round maps. Selecting any allowed
playlist map on the backend could disagree with the client's chosen map.
Original Replay 0x141075360 builds four count/eight-name/round-index pools from
native dvar strings. The state-8 preparation at 0x1410742B0 chooses four maps.
The selector at 0x141070950 calls 0x141070840 to omit prior maps, then uses the
round's unsigned 16-bit part of the full tournament ID. If all pool maps have
been used, it omits only the immediately preceding map. A single-map pool is
always selected. These contracts came from the original 1.20 Replay SQLite/PE;
source from another build supplied behavioral context only.

IMPLEMENTATION
1. One canonical map-pools.json supplies both the backend selector and the four
   native dvar strings in title-5800 general publisher variables. Native names
   come from the existing generated Replay binding table.
2. Schema, full title, revision 1..65535, four pools, one through eight unique
   map names per pool and native/common-playlist string bounds are validated.
   Duplicate keys, trailing data and malformed persisted layouts fail closed.
3. A flushed atomic revision/hash receipt rejects rollback and changed contents
   under an accepted revision. A blocked receipt write cannot publish success.
4. Capacity publications opt in with native_map_pool_revision. The complete
   snapshot is pinned in the competition definition. Changing it under an
   allocated tournament ID cannot mutate that tournament. Publish a new ID.
5. Round allocation requires the native-selected map in the normal playlist
   and available-map policy. Unavailable maps leave the round unallocated.
   Existing authenticated readiness, native lobby documents and recoverable
   bracket/lobby/search/index/enrollment transactions remain in use.
6. No game executable or proxy changes. No seeded players, friendships,
   acceptance flags or production competitions.
